MySQL Vector 使用说明

MySQL Vector 是向量能力扩展，用于在 MySQL 内保存向量、构建向量索引，并通过 SQL 完成语义检索、推荐召回、多模态相似度匹配等工作负载。本手册说明公开 SQL、DDL、构建参数、运行时变量、状态观测和运维建议。

0. 构建依赖配置

向量相关可选依赖优先通过 CMake 参数传入，而不是写死本机路径。

当前支持的参数：

参数 含义
HAVE_VECTOR_INDEX 是否编译 MySQL Vector 特性；向量版本必须显式设置为 ON
MYSQL_VECTOR_FAISS_ROOT Faiss 安装根目录
MYSQL_VECTOR_FAISS_INCLUDE_DIR Faiss 头文件目录
MYSQL_VECTOR_FAISS_LIBRARY_DIR Faiss 库目录
MYSQL_VECTOR_HNSWLIB_ROOT hnswlib 安装根目录
MYSQL_VECTOR_HNSWLIB_INCLUDE_DIR hnswlib 头文件目录
MYSQL_VECTOR_DISKANN_LIB DiskANN 共享库完整路径
MYSQL_VECTOR_DISKANN_LIB_DIR DiskANN 共享库目录
MYSQL_VECTOR_ENABLE_NATIVE_SIMD 是否在编译器支持时为 native 向量后端启用 CPU-native SIMD 编译；默认 ON
MYSQL_VECTOR_FAISS_OPT_LEVEL Faiss 源码编译时的 CPU SIMD 目标；默认留空，由 MySQL 按平台选择

说明：

  • 编译向量版本时必须显式传 -DHAVE_VECTOR_INDEX=ON。如果传 -DHAVE_VECTOR_INDEX=OFF 或不启用该选项，服务端会构建为无向量标准 MySQL 行为版本： 不注册向量函数、向量状态变量、向量事务插件和向量 DD truth-store； VECTOR(dim)、CREATE/DROP VECTOR INDEX、SHOW VECTOR STATUS 等入口会返回 不支持。
  • Faiss 在两种模式下工作：
  • 若 MYSQL_VECTOR_FAISS_ROOT 指向的是带 CMakeLists.txt 的 Faiss 源码树，MySQL 会在构建时直接把 CPU 版 Faiss 一起编出来。
  • 否则回退到传统模式，由 CMake 查找已有的 Faiss 头文件和库文件。
  • Linux 源码编译 Faiss 且 MYSQL_VECTOR_ENABLE_NATIVE_SIMD=ON 时，默认等价于 MYSQL_VECTOR_FAISS_OPT_LEVEL=dd，使用 Faiss 主库的运行时 SIMD dispatch； 需要通用二进制时显式传 -DMYSQL_VECTOR_FAISS_OPT_LEVEL=generic。
  • hnswlib 当前按 header-only 方式集成；MYSQL_VECTOR_HNSWLIB_ROOT 可以直接指向源码树根目录，CMake 会把它作为子目录纳入构建，不要求预先生成独立库文件。
  • MYSQL_VECTOR_ENABLE_NATIVE_SIMD=ON 时，CMake 会仅对 sql/vector/vector_index_backend_hnswlib.cc 选择编译器支持的 -march=native 或 -mcpu=native。这会让 hnswlib 的 header-only 距离计算实例化为当前 CPU 可用的 SIMD 路径；如需构建可搬移到不同 CPU 型号的通用二进制，显式传 -DMYSQL_VECTOR_ENABLE_NATIVE_SIMD=OFF。
  • hnswlib 批量查询默认使用最多 4 个只读 worker；如需在 benchmark 中调优，启动 mysqld 前设置环境变量 MYSQL_VECTOR_HNSWLIB_BATCH_SEARCH_THREADS。当前实现会把 该值限制到硬件线程数和 32 之间。
  • 如果 Faiss 或其他向量依赖在当前系统上通过 OpenBLAS 或 OpenMP 解析 BLAS 符号，且测试中 观察到内部 worker 线程干扰 mysqld 信号处理或 benchmark 可重复性，可以只限制对应 mysqld 或独立 benchmark 实例的启动环境。不要把这类向量测试环境变量写入 mysqld_safe、systemd 模板或其他上游启动脚本；标准 MySQL 构建和无向量构建必须保留 上游启动行为。MTR 中不要在 mysql-test-run.pl 进程环境里 export 这些变量，否则 可能影响 MTR 对 NUMBER_OF_CPUS 的判断，使 resource group 类用例误 skip。 例如：
cmake --build "${BUILD_DEBUG_DIR}" --target mysqld

cd "${BUILD_DEBUG_DIR}/mysql-test"
./mysql-test-run.pl --suite=vector \
  --mysqld-env=OPENBLAS_NUM_THREADS=1 \
  --mysqld-env=OMP_NUM_THREADS=1 \
  --mysqld-env=GOTO_NUM_THREADS=1

如果测试框架之外直接启动 mysqld 或 benchmark client，也应在该进程的全局执行环境中 设置这些变量，而不是依赖 MySQL 启动脚本自动注入。

  • hnswlib bulk build / rebuild 默认使用硬件线程数，并在实际执行时限制到工作量、硬件线程数和 65535 个 worker 之内；也可以通过 全局系统变量 vector_hnsw_build_threads 指定新建 HNSWLIB 索引的默认并行度，或在 VEC_INDEX_CREATE(..., build_threads) / CREATE VECTOR INDEX ... WITH (..., build_threads) 中为单个索引指定。该参数在 HNSWLIB 索引元数据中保存为 hnsw_build_threads。语句级参数 大于 0 时优先级高于全局变量；语句级 0 表示继承全局设置，全局也为 0 时才使用自动策略。
  • Faiss build / rebuild 依赖 Faiss 自身的 OpenMP 并行路径；可以通过全局系统变量 vector_faiss_build_threads 指定新建 FAISS 索引的默认 OpenMP worker 数，或在 VEC_INDEX_CREATE(..., build_threads) / CREATE VECTOR INDEX ... WITH (..., build_threads) 中为单个索引指定。语句级参数 大于 0 时优先级高于全局变量；语句级 0 表示继承全局设置，全局也为 0 时交给 Faiss/OpenMP 自动选择。取值范围为 0..65535。
  • DiskANN native build 默认兼容官方 libdiskann_garnet 串行 C ABI：如果运行时只提供 create_index 和 insert，MySQL-Vector 会逐条调用 insert 完成 shadow build， vector_diskann_build_threads 和语句级 build_threads 只记录在索引配置中，不会改变 官方串行 ABI 的并行度。若需要实验性的 DiskANN 并行 bulk build，先在 DiskANN Garnet 源码上应用 extra/vector/diskann-garnet-bulk-build-c-abi.patch，重新构建 libdiskann_garnet；MySQL-Vector 只有在运行时同时探测到 create_index_with_build_threads 和 bulk_insert 两个扩展符号时，才会把 build_threads 传给 DiskANN 并调用 bulk_insert。该并行路径目前用于性能实验；稳定 场景优先使用官方串行 ABI。
  • vector_diskann_build_threads 可指定新建 DiskANN 索引的默认并行度，或在 VEC_INDEX_CREATE(..., build_threads) / CREATE VECTOR INDEX ... WITH (..., build_threads) 中为单个索引指定。语句级参数 大于 0 时优先级高于全局变量；语句级 0 表示继承全局设置，全局也为 0 时由 DiskANN runtime 自动选择；显式取值范围为 0..65535。在未应用上述实验 ABI patch 的 官方串行 DiskANN 共享库上，该参数只保留配置语义，不产生并行效果。
  • DiskANN 当前在运行时通过 dlopen() 加载 libdiskann_garnet，因此需要传共享库完整路径，或至少传共享库目录。
  • MYSQL_VECTOR_DISKANN_LIB_DIR 必须指向实际包含 libdiskann_garnet.dylib / libdiskann_garnet.so 的目录，而不是任意上层目录。
  • CMake 也会读取同名环境变量 MYSQL_VECTOR_FAISS_ROOT、MYSQL_VECTOR_FAISS_INCLUDE_DIR、 MYSQL_VECTOR_FAISS_LIBRARY_DIR、MYSQL_VECTOR_HNSWLIB_ROOT、 MYSQL_VECTOR_HNSWLIB_INCLUDE_DIR、MYSQL_VECTOR_DISKANN_LIB 和 MYSQL_VECTOR_DISKANN_LIB_DIR 作为默认值，便于本地临时构建；可复现构建和 CI 应优先显式传 CMake 参数。

示例：

BUILD_ROOT=../build/mysql-vector
BUILD_DEBUG_DIR="${BUILD_ROOT}/build-debug"
BOOST_ROOT="${BUILD_ROOT}/deps"
FAISS_ROOT=../deps/FAISS
HNSWLIB_ROOT=../deps/HNSWLib
DISKANN_LIB_DIR=../deps/DiskANN/target/release

cmake -S . -B "${BUILD_DEBUG_DIR}" -G Ninja \
-DCMAKE_BUILD_TYPE=Debug \
-DWITH_DEBUG=1 \
-DHAVE_VECTOR_INDEX=ON \
-DWITH_NDB=OFF \
-DWITH_NDBCLUSTER_STORAGE_ENGINE=OFF \
-DDOWNLOAD_BOOST=1 \
-DWITH_BOOST="${BOOST_ROOT}" \
-DMYSQL_VECTOR_FAISS_ROOT="${FAISS_ROOT}" \
-DMYSQL_VECTOR_HNSWLIB_ROOT="${HNSWLIB_ROOT}" \
-DMYSQL_VECTOR_DISKANN_LIB_DIR="${DISKANN_LIB_DIR}"

DiskANN 实验并行 ABI patch 示例：

MYSQL_SOURCE_DIR=.
DISKANN_SOURCE_DIR=../deps/DiskANN

git -C "${DISKANN_SOURCE_DIR}" apply \
"${MYSQL_SOURCE_DIR}/extra/vector/diskann-garnet-bulk-build-c-abi.patch"
cargo build --manifest-path "${DISKANN_SOURCE_DIR}/Cargo.toml" \
-p diskann-garnet --release

-DMYSQL_VECTOR_FAISS_ROOT="${FAISS_INSTALL_ROOT}" \

0.2 升级保护参数

从没有向量数据字典的旧版本升级到向量版本时，推荐先使用旧版本执行一次干净关机：

SET GLOBAL innodb_fast_shutdown = 0;

然后正常关闭旧版本，再启动向量版本。

向量版本提供启动参数：

innodb_vector_upgrade_require_clean_shutdown = ON

该参数默认 OFF，不改变 MySQL 原有升级行为。若设置为 ON，服务器在升级到向量数据 字典版本前会检查本次启动是否执行了 InnoDB redo recovery；如果旧数据目录需要 redo 恢复，则拒绝升级并要求先回到旧版本用 innodb_fast_shutdown=0 干净关机后再升级。

使用建议：

  • 生产升级窗口建议显式设置 --innodb-vector-upgrade-require-clean-shutdown=ON，把“旧版本异常关机后直接升级到向量 版本”的场景提前阻断。
  • 若已有升级流程可以保证旧版本干净关机，该参数可以保持默认 OFF。
  • 该参数是启动期只读参数，不能在运行时修改，也不会被 SET PERSIST 持久化。

1. 向量列

1.1 语法

VECTOR(dim)
  • dim 必须是正整数。
  • SHOW CREATE TABLE、SHOW COLUMNS、DESCRIBE、INFORMATION_SCHEMA 中都显示为 VECTOR(dim)。

示例：

CREATE TABLE t_vec (
id BIGINT PRIMARY KEY,
emb VECTOR(4)
) ENGINE=InnoDB;

1.2 写入建议

  • 文本字面量建议统一先通过 VEC_FROMTEXT('[1,2,3]') 转成内部向量值。
  • 写入值的维度必须和列定义一致，否则会报错。

2. 基础向量函数和枚举参数

2.1 枚举参数

metric、mode、provider 解析不区分大小写，前后空白会被忽略。

参数 支持值 含义
metric EUCLIDEAN、L2 欧氏距离，返回 sqrt(sum((lhs-rhs)^2))，值越小越相似
metric COSINE 余弦距离，返回 1 - cosine_similarity，值越小越相似，零向量不可计算
metric IP、INNER_PRODUCT 内积距离。VEC_INNER_PRODUCT() 返回原始内积；VEC_DISTANCE(..., 'IP') 返回 -dot(lhs,rhs)，用于保持“距离越小越相似”的排序语义
mode MEMORY 内存服务态索引
mode EXTERNAL 带外部持久化 sidecar 的索引
provider NATIVE 内置后端，支持 MEMORY 和 EXTERNAL
provider FAISS Faiss 后端，常用于 EXTERNAL；支持 hnsw、ivf_flat、ivf_pq 变体
provider DISKANN DiskANN 后端，只支持 EXTERNAL
provider HNSWLIB、HNSW hnswlib 后端，只支持 MEMORY

不支持的 mode/provider 组合会在创建索引时失败，例如 DISKANN/MEMORY 和 HNSWLIB/EXTERNAL。

2.2 基础函数参考

函数名 函数行为 输入参数含义 返回值含义
VEC_FROMTEXT(text) 把文本向量字面量编码成 MySQL 内部 VECTOR 二进制格式 text：形如 '[1,2,3]' 的浮点数组文本 二进制向量值；直接展示不可读，排查时用 HEX(...) 或 VEC_TOTEXT(...)
VEC_TOTEXT(vector_expr) 把内部二进制向量解码为文本 vector_expr：VECTOR 列值或 VEC_FROMTEXT(...) 结果 文本向量，如 [1,2,3]
VECTOR_DIM(vector_expr) 读取向量维度 vector_expr：二进制向量值 向量元素个数
VEC_NORMALIZE(vector_expr) 对向量做 L2 归一化 vector_expr：非零二进制向量值 归一化后的二进制向量
VEC_DOT_PRODUCT(lhs, rhs) 计算两个同维向量点积 lhs、rhs：同维二进制向量值 原始点积 sum(lhs[i] * rhs[i])
VEC_INNER_PRODUCT(lhs, rhs) 计算两个同维向量内积 lhs、rhs：同维二进制向量值 原始内积；当前与 VEC_DOT_PRODUCT() 等价
VEC_DISTANCE_EUCLIDEAN(lhs, rhs) 计算两个同维向量欧氏距离 lhs、rhs：同维二进制向量值 sqrt(sum((lhs-rhs)^2))
VEC_DISTANCE_COSINE(lhs, rhs) 计算两个同维向量余弦距离 lhs、rhs：同维非零二进制向量值 1 - cosine_similarity
VEC_DISTANCE(lhs, rhs[, metric]) 按指定度量计算通用距离 lhs、rhs：同维二进制向量值；metric：可选，见 2.1 距离值；IP/INNER_PRODUCT 返回负内积，以保持距离升序语义

  • VEC_FROMTEXT() 的直接返回值是内部二进制向量，手工排查时建议用 HEX(...) 或 VEC_TOTEXT(...) 包起来查看。

3. 独立命名索引函数

独立命名索引由 VEC_INDEX_CREATE() 创建，不绑定表列，不会出现在 SHOW CREATE TABLE 中。调用方需要显式 UPSERT、ERASE、事务提交、重建和恢复。

默认值：

  • metric='euclidean'
  • mode='memory'
  • provider='native'

3.1 生命周期、写入和查询函数参考

函数名 函数行为 输入参数含义 返回值含义
VEC_INDEX_CREATE(index_name, dim[, metric[, mode[, provider[, build_threads]]]]) 创建独立命名向量索引 index_name：索引名；dim：维度；metric、mode、provider：可选枚举，见 2.1；build_threads：HNSWLIB、FAISS 或 DiskANN build / rebuild worker 数，0 表示继承对应 provider 的全局设置 1 表示创建成功，失败时报错
VEC_INDEX_DROP(index_name) 删除独立命名向量索引 index_name：索引名 1 表示删除成功，0 表示索引不存在或未删除
VEC_INDEX_UPSERT(index_name, doc_id, vector_expr) 插入或覆盖一个文档向量 index_name：索引名；doc_id：无符号 64 位整数文档 ID；vector_expr：向量值 1 表示写入成功
VEC_INDEX_ERASE(index_name, doc_id) 删除一个文档向量 index_name：索引名；doc_id：无符号 64 位整数文档 ID 1 表示删除成功
VEC_INDEX_SEARCH(index_name, query_vector_expr, top_k) 近邻搜索，只返回文档 ID index_name：索引名；query_vector_expr：查询向量；top_k：候选数量，范围 0..10000，0 返回空结果 JSON 文本数组，如 [1,2]
VEC_INDEX_SEARCH_BATCH(index_name, query_batch_expr, query_count, top_k) 批量近邻搜索，只返回文档 ID；无 pending 事务和 mapped MVCC 回表过滤时可走后端批量并行搜索 index_name：索引名；query_batch_expr：query_count 个同维二进制向量的连续拼接；query_count：查询数量，范围 1..1024；top_k：每个查询返回数量，范围 0..10000；query_count * top_k 不能超过 65536 JSON 文本二维数组，如 [[1,2],[2,1]]
VEC_INDEX_SEARCH_WITH_DISTANCE(index_name, query_vector_expr, top_k) 近邻搜索，返回文档 ID 和距离 参数同 VEC_INDEX_SEARCH() JSON 文本数组，元素包含 doc_id 和 distance
VEC_INDEX_INFO(index_name) 查询索引配置、状态和计数 index_name：索引名 JSON 文本对象
VEC_INDEX_LIST() 列出当前注册的向量索引 无 JSON 文本数组，元素为索引名
VEC_INDEX_BULK_LOAD_BEGIN(index_name) 进入 bulk-load 模式，后续事务只写 committed truth rows，暂不更新 serving backend index_name：索引名；要求该索引没有未提交 staged 变更 1 表示进入 bulk-load 成功
VEC_INDEX_BULK_BUILD(index_name) 从 committed truth rows 构建 shadow backend 并原子替换 serving backend；hnswlib 后端按索引配置的 hnsw_build_threads 并行建图；Faiss 后端按索引配置的 faiss_build_threads 设置 OpenMP worker；DiskANN native 后端优先探测实验扩展 ABI，存在 create_index_with_build_threads 和 bulk_insert 时调用 bulk_insert 批量建图，否则回退到官方串行 insert 路径；构建期 native store 先写内存，成功后一次性 flush 到持久化目录，成功路径不生成 FAISS/DiskANN sidecar index_name：索引名 1 表示 bulk build 成功
VEC_INDEX_REBUILD(index_name) 用 committed entries 重建单个索引服务态；实现上使用 shadow backend，锁内捕获快照，锁外构建，成功后再短锁校验并替换 live backend；hnswlib 后端可并行建图；Faiss 后端可临时设置 OpenMP worker；DiskANN native 后端按运行时 ABI 能力选择实验 bulk insert 或官方串行 insert，并使用同一构建期内存 store flush 路径 index_name：索引名 1 表示重建成功
VEC_INDEX_RECOVER(index_name) 从持久化 sidecar 或 committed entries 恢复单个索引；锁外构建 recovered shadow backend，成功后短锁安装 index_name：索引名 1 表示恢复成功
VEC_INDEX_REBUILD_ALL() 重建全部已注册索引；锁外逐个构建 shadow backend，全部校验通过后批量安装 无 成功重建的索引数量
VEC_INDEX_RECOVER_ALL() 恢复全部已注册索引；锁外逐个构建 recovered shadow backend，全部校验通过后批量安装 无 成功恢复的索引数量

VEC_INDEX_LIST()、VEC_INDEX_SEARCH()、VEC_INDEX_SEARCH_BATCH()、 VEC_INDEX_SEARCH_WITH_DISTANCE() 和 VEC_INDEX_INFO() 返回的是 JSON 文本，不是原生 JSON 列类型。

特别说明：

  • VEC_INDEX_SET_FAISS_IVF_PARAMS(index_name, 0, 0) 会切回 Faiss hnsw 变体。
  • 构建期参数会保存到索引配置；如需立刻让构建期参数生效，显式执行 VEC_INDEX_REBUILD(...) 或 VEC_INDEX_REBUILD_ALL()。
  • Faiss build worker 数当前只在创建索引、bulk build、rebuild 和内存后端批量加载时 生效。它不会改变查询并行度；查询批量路径由 Faiss Index::search(nq, ...) 自身调度。
  • DiskANN native build / rebuild 在构建期间不会直接重写持久化 native store； 只有 native build 和内存 store flush 都成功后才替换持久化目录。失败时旧 serving backend 和旧 native store 继续保留。
  • DiskANN native build / rebuild 成功后，当前 mysqld 进程会继续持有 resident native store 服务查询，优先从内存 resident store 响应 DiskANN callback； 持久化目录用于重启恢复或 resident miss fallback。该路径减少查询期逐 key 文件打开 开销，但会增加与 native store 大小相关的进程内存占用。
  • 运行态调参只持久化索引 metadata 和 manifest，不应重写已提交向量数据、change log 或 prepared 事务记录。实现采用两阶段模型：先构造候选 backend/config，再持久化 metadata/manifest，成功后才切换 live 配置；如果持久化失败，旧配置继续生效并返回 错误。

4. 显式事务缓冲函数

显式事务函数用于把多次向量写入作为一组提交或回滚。单次直接写入优先使用 VEC_INDEX_UPSERT() / VEC_INDEX_ERASE()。

CREATE VECTOR INDEX IF NOT EXISTS ON tbl(col) WITH (dim)
CREATE VECTOR INDEX ON tbl(col) WITH (dim, metric, mode, provider)
CREATE VECTOR INDEX ON tbl(col) WITH (dim, metric, mode, provider, build_threads)

DROP VECTOR INDEX ON tbl(col)
DROP VECTOR INDEX IF EXISTS ON tbl(col)

WITH 参数含义：

  • dim：向量维度，必须大于 0。
  • metric：支持 EUCLIDEAN、L2、COSINE、IP、INNER_PRODUCT。
  • mode：支持 MEMORY、EXTERNAL。
  • provider：支持 NATIVE、FAISS、DISKANN、HNSWLIB、HNSW。
  • build_threads：仅用于 provider='HNSWLIB'、provider='FAISS' 或 provider='DISKANN'，取值 0..65535；大于 0 的语句级参数优先于对应全局变量 vector_hnsw_build_threads、vector_faiss_build_threads 或 vector_diskann_build_threads，语句级 0 表示继承全局设置，全局 0 表示自动。

5.2 VEC_INDEX_CREATE 与 CREATE VECTOR INDEX 的区别

维度 VEC_INDEX_CREATE(...) CREATE VECTOR INDEX ON tbl(col)
索引名称 调用方传入任意独立名称，如 idx_fn 自动使用 schema.table.column，如 readme_vector.t_ddl.v
表绑定 不绑定表列 绑定一个 InnoDB VECTOR(dim) 列
数据来源 调用方显式 VEC_INDEX_UPSERT() / VEC_INDEX_ERASE() 建索引时 backfill 已有行，后续普通 DML 自动同步
元数据导出 不出现在 SHOW CREATE TABLE SHOW CREATE TABLE 会导出 CREATE VECTOR INDEX 定义
适用场景 benchmark、外部客户端自管 doc_id、自定义导入管线 生产表列索引、随表生命周期管理

5.3 使用限制

  • 目标列必须是 VECTOR(dim) 列，且 WITH (dim) 必须和列维度一致。
  • CREATE VECTOR INDEX 当前只支持 InnoDB 基表；非 InnoDB 表会被拒绝。
  • 当前映射索引要求表具有单列、非空、整数主键作为 doc_id；无符号整数主键支持完整 uint64_t 范围，有符号整数主键的负值不作为有效 doc_id。
  • 不支持临时表上的 CREATE VECTOR INDEX / DROP VECTOR INDEX。
  • CREATE VECTOR INDEX backfill 期间会持有 no-write 元数据锁，以避免扫描快照覆盖并发 DML 已提交的向量变更。
  • CREATE VECTOR INDEX 内部使用 creating -> backfilling -> ready 生命周期。 如果 mysqld 在 ready 前重启，恢复会清理未完成索引的 metadata、committed entries、 changelog 和 prepared rows，不会把半成品索引暴露给查询。

5.4 生命周期联动

以下表级操作会自动同步向量索引生命周期：

  • CREATE TABLE ... LIKE
  • RENAME TABLE
  • ALTER TABLE ... RENAME TO
  • ALTER TABLE ... RENAME COLUMN
  • ALTER TABLE ... CHANGE/MODIFY COLUMN
  • ALTER TABLE ... DROP COLUMN
  • TRUNCATE TABLE
  • DROP TABLE
  • DROP DATABASE

字段后缀 含义

SYNC_PIPELINE 字段：

字段后缀 含义
pending_apply_count entry_count 与 committed_entry_count 的非负差值；bulk-load 期间通常等于已提交但尚未进入 serving backend 的条目数
apply_latency_ms 最近一次应用变更耗时
rebuild_progress 重建状态指示：100 表示 ready，50 表示 rebuilding，其他状态为 0
recover_progress 恢复状态指示：100 表示 ready，50 表示 recovering，其他状态为 0

生命周期状态值：

值 含义
ready 索引可读写，最近一次创建、重建、恢复或提交已完成
creating 表级 CREATE VECTOR INDEX 已持久化 metadata，但尚未开始 backfill；重启恢复会清理该未完成 DDL 状态
backfilling 表级 CREATE VECTOR INDEX 正在扫描基表并构建初始 committed/serving 快照；查询会失败，重启恢复会清理该未完成 DDL 状态
bulk_loading 索引处于 bulk-load 模式，提交只更新 truth rows；查询会失败，直到执行 VEC_INDEX_BULK_BUILD() 或 VEC_INDEX_REBUILD() 成功
rebuilding 正在重建服务态索引；当前同步 rebuild API 使用锁外 shadow 构建，通常只在显式诊断状态中可见
recovering 正在从持久化状态或 committed entries 恢复；当前同步 recover API 使用锁外 shadow 构建，通常只在显式诊断状态中可见
failed 最近一次生命周期操作失败，查看 last_error_code 和 last_error_ts

错误码：

错误码 含义
0 无错误
1001 存在未提交变更，当前操作不能安全执行
1002 创建后端失败
1003 后端恢复失败
1004 committed entries 重放失败
1005 后端不支持 mutation
1006 后端应用变更失败

7. 使用建议

  • 文本向量输入统一使用 VEC_FROMTEXT(...)，避免客户端二进制编码差异。
  • 面向表列的生产路径优先用表级 DDL 与正常 DML，同步行为更直观。
  • 需要 HNSW / Faiss / DiskANN 调参时，先确认索引当前的 mode/provider。
  • 读取机器可消费结果时，把 VEC_INDEX_INFO() / VEC_INDEX_SEARCH*() 当作 JSON 文本处理。
  • 批量修改索引参数后，如需立刻让构建期参数生效，显式执行 VEC_INDEX_REBUILD(...)。

7.1 Benchmark 与压测经验

  • 接入外部 benchmark 前，建议先用小规模数据集确认建表、建索引、写入、查询和参数映射都正常，再切到大数据集。
  • 高维大批量导入优先使用独立命名索引快路径：
    • VEC_INDEX_CREATE 创建索引。
    • VEC_INDEX_STAGE_UPSERT 批量暂存向量。
    • VEC_INDEX_TXN_COMMIT 分批提交。
    • VEC_INDEX_BULK_BUILD 或 VEC_INDEX_REBUILD 一次性构建服务态索引。
    • VEC_INDEX_SEARCH 执行查询。
  • 大规模导入建议客户端直接传 float32 二进制向量载荷；VEC_FROMTEXT('[...]') 更适合作为 SQL 示例、小规模 smoke 和手工排查入口。
  • 长时间压测建议使用独立 mysqld 实例，并为 innodb_redo_log_capacity、innodb_buffer_pool_size 和后端 build threads 预留足够资源，避免把 redo 回收、buffer pool 抖动或过低并行度误判为向量索引瓶颈。
  • 如果 benchmark runner 把 load、optimize、search 放在不同进程中，后续进程应先用 VEC_INDEX_INFO(index_name) 重新附着已有索引状态，不要盲目重复 VEC_INDEX_CREATE(...)。
  • 如果 VEC_INDEX_INFO() 返回的 search_ef 已经等于目标值，通常不需要重复执行 VEC_INDEX_SET_SEARCH_EF(...)；重复下发只会更新 metadata/manifest。
  • 压测过程变慢或中断时，先区分是客户端导入路径慢还是服务端索引构建慢：
    • 用 SHOW PROCESSLIST 查看当前会话正在执行的 SQL。
    • 用 SHOW GLOBAL STATUS LIKE 'Vector_%' 查看写入、提交、持久化和搜索计数。

Vector-related optional dependencies should be passed through CMake options instead of hard-coded local paths.

Currently supported options:

Option Meaning

MYSQL_VECTOR_FAISS_INCLUDE_DIR Faiss header directory for a prebuilt Faiss installation.
MYSQL_VECTOR_FAISS_LIBRARY_DIR Directory that contains prebuilt Faiss libraries.

MYSQL_VECTOR_HNSWLIB_INCLUDE_DIR hnswlib header directory when no source root is provided.
MYSQL_VECTOR_DISKANN_LIB / MYSQL_VECTOR_DISKANN_LIB_DIR DiskANN Garnet shared library path or directory. DiskANN is loaded at runtime through dlopen().
MYSQL_VECTOR_ENABLE_NATIVE_SIMD Enables native SIMD flags for supported vector backend compilation units.
MYSQL_VECTOR_FAISS_OPT_LEVEL Selects the Faiss SIMD target, such as generic, avx2, avx512, avx512_spr, sve, or runtime-dispatch dd.

Notes:

  • Vector builds must pass -DHAVE_VECTOR_INDEX=ON explicitly. If -DHAVE_VECTOR_INDEX=OFF is passed, or the option is not enabled, the server is built with standard no-vector MySQL behavior: vector functions, vector status variables, the vector transaction plugin, and vector DD truth-store are not registered; VECTOR(dim), CREATE/DROP VECTOR INDEX, and SHOW VECTOR STATUS return unsupported errors.
  • Faiss has two build modes:
  • If MYSQL_VECTOR_FAISS_ROOT points to a Faiss source tree with CMakeLists.txt, MySQL builds the CPU Faiss library as part of the MySQL build.
  • Otherwise CMake falls back to the traditional mode and looks for existing Faiss headers and libraries.
  • When Faiss is built from source on Linux and MYSQL_VECTOR_ENABLE_NATIVE_SIMD=ON, the default is equivalent to MYSQL_VECTOR_FAISS_OPT_LEVEL=dd, using Faiss runtime SIMD dispatch in the main library; pass -DMYSQL_VECTOR_FAISS_OPT_LEVEL=generic explicitly when a portable binary is required.
  • hnswlib is integrated as a header-only backend. MYSQL_VECTOR_HNSWLIB_ROOT can point directly to the source root; CMake adds it as a subdirectory and does not require a prebuilt standalone library.
  • When MYSQL_VECTOR_ENABLE_NATIVE_SIMD=ON, CMake applies the supported -march=native or -mcpu=native flag only to sql/vector/vector_index_backend_hnswlib.cc. This lets hnswlib distance kernels instantiate SIMD code for the current CPU. To build a portable binary for different CPU models, pass -DMYSQL_VECTOR_ENABLE_NATIVE_SIMD=OFF.
  • hnswlib batch search uses up to 4 read-only workers by default. For benchmark tuning, set MYSQL_VECTOR_HNSWLIB_BATCH_SEARCH_THREADS before starting mysqld. The implementation clamps the value to the hardware thread count and 32.
  • If Faiss or another vector dependency resolves BLAS symbols through OpenBLAS or OpenMP on the current system, and tests show internal worker threads interfering with mysqld signal handling or benchmark repeatability, limit only the startup environment of the tested mysqld or standalone benchmark instance. Do not inject these vector-test environment variables into mysqld_safe, systemd templates, or other upstream startup scripts; standard MySQL builds and no-vector builds must keep upstream startup behavior. In MTR, do not export these variables in the mysql-test-run.pl process environment, because that can affect MTR's NUMBER_OF_CPUS detection and incorrectly skip resource group tests. Example:
cmake --build "${BUILD_DEBUG_DIR}" --target mysqld

cd "${BUILD_DEBUG_DIR}/mysql-test"
./mysql-test-run.pl --suite=vector \
  --mysqld-env=OPENBLAS_NUM_THREADS=1 \
  --mysqld-env=OMP_NUM_THREADS=1 \
  --mysqld-env=GOTO_NUM_THREADS=1

If mysqld or a benchmark client is started directly outside the test framework, set these variables in that process environment rather than relying on MySQL startup scripts to inject them.

  • hnswlib bulk build / rebuild uses the hardware thread count by default and clamps the actual worker count to the workload size, hardware thread count, and 65535. The global system variable vector_hnsw_build_threads can specify the default parallelism for new HNSWLIB indexes, and VEC_INDEX_CREATE(..., build_threads) / CREATE VECTOR INDEX ... WITH (..., build_threads) can override it per index. The value is stored in HNSWLIB index metadata as hnsw_build_threads. A statement-level value greater than 0 takes precedence over the global variable; statement-level 0 means inherit the global setting, and only a global 0 selects the automatic strategy.
  • Faiss build / rebuild relies on Faiss's OpenMP parallel path. The global system variable vector_faiss_build_threads can specify the default OpenMP worker count for new FAISS indexes, and VEC_INDEX_CREATE(..., build_threads) / CREATE VECTOR INDEX ... WITH (..., build_threads) can override it per index. A statement-level value greater than 0 takes precedence over the global variable; statement-level 0 means inherit the global setting, and a global 0 lets Faiss/OpenMP choose automatically. The range is 0..65535.
  • DiskANN native build is compatible by default with the official libdiskann_garnet serial C ABI. If only create_index and insert are available at runtime, MySQL-Vector calls insert row by row to complete shadow build. vector_diskann_build_threads and statement-level build_threads are recorded in index configuration but do not change the parallelism of the official serial ABI. To use the experimental DiskANN parallel bulk build path, first apply extra/vector/diskann-garnet-bulk-build-c-abi.patch to DiskANN Garnet and rebuild libdiskann_garnet. MySQL-Vector passes build_threads to DiskANN and calls bulk_insert only when it detects both create_index_with_build_threads and bulk_insert runtime symbols. This parallel path is intended for performance experiments; stable scenarios should prefer the official serial ABI.
  • vector_diskann_build_threads can specify the default parallelism for new DiskANN indexes, and VEC_INDEX_CREATE(..., build_threads) / CREATE VECTOR INDEX ... WITH (..., build_threads) can override it per index. A statement-level value greater than 0 takes precedence over the global variable; statement-level 0 means inherit the global setting, and a global 0 lets the DiskANN runtime choose automatically. Explicit values use the range 0..65535. With an unpatched official serial DiskANN shared library, this setting only preserves configuration semantics and does not create parallelism.
  • DiskANN is loaded at runtime through dlopen(), so pass either the full shared-library path or at least the shared-library directory.
  • MYSQL_VECTOR_DISKANN_LIB_DIR must point to the directory that actually contains libdiskann_garnet.dylib / libdiskann_garnet.so, not an arbitrary parent directory.
  • CMake also reads the same-named environment variables MYSQL_VECTOR_FAISS_ROOT, MYSQL_VECTOR_FAISS_INCLUDE_DIR, MYSQL_VECTOR_FAISS_LIBRARY_DIR, MYSQL_VECTOR_HNSWLIB_ROOT, MYSQL_VECTOR_HNSWLIB_INCLUDE_DIR, MYSQL_VECTOR_DISKANN_LIB, and MYSQL_VECTOR_DISKANN_LIB_DIR as defaults for temporary local builds. 0.2 Upgrade Guard Parameter

When upgrading from an old version without the vector data dictionary to a vector version, it is recommended to perform one clean shutdown with the old version first:

SET GLOBAL innodb_fast_shutdown = 0;

Then shut down the old version normally and start the vector version.

The vector version provides this startup option:

innodb_vector_upgrade_require_clean_shutdown = ON

The default is OFF, so the original MySQL upgrade behavior is unchanged. If set to ON, the server checks whether this startup performed InnoDB redo recovery before upgrading to the vector data dictionary version. If the old data directory requires redo recovery, the upgrade is rejected and the user must return to the old version, shut it down cleanly with innodb_fast_shutdown=0, and then upgrade again.

Usage recommendations:

  • During production upgrade windows, explicitly set --innodb-vector-upgrade-require-clean-shutdown=ON to block direct upgrade to the vector version after an abnormal old-version shutdown.
  • If the existing upgrade process already guarantees a clean old-version shutdown, this option can stay at the default OFF.
  • This option is a startup-time read-only parameter. It cannot be changed at runtime and is not persisted by SET PERSIST.

3. Standalone Named Index Functions

Standalone named indexes are created by VEC_INDEX_CREATE(). They are not bound to table columns and do not appear in SHOW CREATE TABLE. Callers explicitly perform UPSERT, ERASE, transaction commit, rebuild, and recovery.

Defaults:

  • metric='euclidean'
  • mode='memory'
  • provider='native'

Special notes:

  • VEC_INDEX_SET_FAISS_IVF_PARAMS(index_name, 0, 0) switches back to the Faiss hnsw variant.
  • Build-time parameters are saved in index configuration. To make build-time parameters take effect immediately, run VEC_INDEX_REBUILD(...) or VEC_INDEX_REBUILD_ALL() explicitly.
  • Faiss build worker count currently applies only when creating an index, bulk building, rebuilding, and bulk-loading an in-memory backend. It does not change query parallelism; batch query execution is scheduled by Faiss Index::search(nq, ...) itself.
  • DiskANN native build / rebuild does not rewrite the persistent native store directly during construction. The persistent directory is replaced only after both native build and memory-store flush succeed. On failure, the old serving backend and old native store remain available.
  • After DiskANN native build / rebuild succeeds, the current mysqld process keeps a resident native store to serve queries and preferentially answers DiskANN callbacks from that resident store. The persistent directory is used for restart recovery or resident-miss fallback. This reduces per-key file open overhead during query execution, but increases process memory usage according to native-store size.
  • Runtime tuning persists only index metadata and manifest checkpoints. It should not rewrite committed vector data, the change log, or prepared transaction records. The implementation uses a two-phase model: build candidate backend/config first, persist metadata/manifest, and switch the live configuration only after persistence succeeds. If persistence fails, the old configuration stays effective and an error is returned.

4. Explicit Transaction Buffer Functions

Explicit transaction functions are used to commit or roll back multiple vector writes as a group. For single direct writes, prefer VEC_INDEX_UPSERT() / VEC_INDEX_ERASE().

Normal SQL transactions for real table-mapped indexes participate in the MySQL savepoint protocol through the hidden handlerton. SAVEPOINT name, ROLLBACK TO SAVEPOINT name, and RELEASE SAVEPOINT name trim or release staged vector changes together with the SQL transaction. Explicit VEC_INDEX_TXN_* savepoint functions are only for directly managing standalone vector transaction buffers.

Function Behavior Input parameters Return value
VEC_INDEX_TXN_BEGIN() Starts an explicit vector transaction. None. Transaction id allocated inside the current instance.
VEC_INDEX_STAGE_UPSERT(index_name, txn_id, id, vector) Stages an upsert in a vector transaction. index_name: index name; txn_id: transaction id; id: unsigned 64-bit document id; vector: vector value. 1 on success.
VEC_INDEX_STAGE_ERASE(index_name, txn_id, id) Stages an erase in a vector transaction. index_name: index name; txn_id: transaction id; id: unsigned 64-bit document id. 1 on success.
VEC_INDEX_TXN_PENDING(txn_id) Returns the number of staged changes in a transaction buffer. txn_id: transaction id. Pending upsert / erase count.
VEC_INDEX_TXN_SAVEPOINT(txn_id, name) Creates a vector transaction savepoint. txn_id: transaction id; name: savepoint name. 1 on success.
VEC_INDEX_TXN_ROLLBACK_TO(txn_id, name) Rolls back staged vector changes to the named savepoint. txn_id: transaction id; name: savepoint name. 1 on success.
VEC_INDEX_TXN_RELEASE_SAVEPOINT(txn_id, name) Releases a vector transaction savepoint. txn_id: transaction id; name: savepoint name. 1 on success.
VEC_INDEX_TXN_COMMIT(txn_id) Commits staged changes. txn_id: transaction id. 1 on success.
VEC_INDEX_TXN_ROLLBACK(txn_id) Rolls back staged changes. txn_id: transaction id. 1 on success.

5. Table-Level DDL

5.1 Syntax

CREATE VECTOR INDEX ON tbl(col) WITH (dim)
CREATE VECTOR INDEX IF NOT EXISTS ON tbl(col) WITH (dim)
CREATE VECTOR INDEX ON tbl(col) WITH (dim, metric, mode, provider)
CREATE VECTOR INDEX ON tbl(col) WITH (dim, metric, mode, provider, build_threads)

DROP VECTOR INDEX ON tbl(col)
DROP VECTOR INDEX IF EXISTS ON tbl(col)

WITH parameter meanings:

  • dim: vector dimension; must be greater than 0.
  • metric: supports EUCLIDEAN, L2, COSINE, IP, and INNER_PRODUCT.
  • mode: supports MEMORY and EXTERNAL.
  • provider: supports NATIVE, FAISS, DISKANN, HNSWLIB, and HNSW.
  • build_threads: only applies to provider='HNSWLIB', provider='FAISS', or provider='DISKANN'. The range is 0..65535. A statement-level value greater than 0 overrides the corresponding global variable vector_hnsw_build_threads, vector_faiss_build_threads, or vector_diskann_build_threads; statement-level 0 means inherit the global setting, and global 0 means automatic.

Table-level vector indexes bind an InnoDB table column to a vector serving index. The index name is derived from schema, table, and column metadata rather than supplied in the SQL statement. DML updates are propagated through the vector transaction bridge and recover from truth rows.

CREATE TABLE t_ddl (
  id BIGINT PRIMARY KEY,
  v VECTOR(2)
) ENGINE=InnoDB;

CREATE VECTOR INDEX ON t_ddl(v)
WITH (2, 'euclidean', 'memory', 'native');

SHOW CREATE TABLE t_ddl\G
*************************** 1. row ***************************
       Table: t_ddl
Create Table: CREATE TABLE `t_ddl` (
  `id` bigint NOT NULL,
  `v` vector(2) DEFAULT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
CREATE VECTOR INDEX ON `t_ddl`(`v`) WITH (2, 'euclidean', 'memory', 'native')

5.2 VEC_INDEX_CREATE vs CREATE VECTOR INDEX

Area VEC_INDEX_CREATE() CREATE VECTOR INDEX
Target Standalone named index. InnoDB table column.
Lifecycle Controlled by scalar SQL functions. Controlled by table DDL and normal DML.
Persistence Metadata and truth rows are persistent. Table binding is persisted through DD metadata.
Typical use Smoke tests, benchmarks, explicit lifecycle control. Application tables and production-style usage.

5.3 Usage Limits

  • The target column must be a VECTOR(dim) column, and WITH (dim) must match the column dimension.
  • CREATE VECTOR INDEX currently supports only InnoDB base tables; non-InnoDB tables are rejected.
  • Mapped indexes currently require a single-column, non-null integer primary key as doc_id. Unsigned integer primary keys support the full uint64_t range; negative signed integer primary-key values are not valid doc_id values.
  • CREATE VECTOR INDEX / DROP VECTOR INDEX is not supported on temporary tables.
  • CREATE VECTOR INDEX holds a no-write metadata lock during backfill to avoid having the scan snapshot overwrite vector changes committed by concurrent DML.
  • CREATE VECTOR INDEX internally uses the creating -> backfilling -> ready lifecycle. If mysqld restarts before ready, recovery cleans up metadata, committed entries, change log, and prepared rows for the incomplete index, and it does not expose a half-built index to queries.

5.4 Lifecycle Coupling

The following table-level operations automatically synchronize the vector index lifecycle:

  • CREATE TABLE ... LIKE
  • RENAME TABLE
  • ALTER TABLE ... RENAME TO
  • ALTER TABLE ... RENAME COLUMN
  • ALTER TABLE ... CHANGE/MODIFY COLUMN
  • ALTER TABLE ... DROP COLUMN
  • TRUNCATE TABLE
  • DROP TABLE
  • DROP DATABASE

6.1 SHOW VECTOR STATUS

Supported forms:

SHOW VECTOR STATUS;

Notes:

  • Requires the global PROCESS privilege.
  • This interface is recommended for automated collection.
  • WHERE currently supports =, !=, <>, LIKE, and NOT LIKE on Section, Variable_name, and Value, plus >, >=, <, and <= comparisons on Value. Predicates can be combined with AND / OR. IN (...) is not supported.

Section meanings:

Section Meaning
GLOBAL Global counters, manifest checkpoints, and truth-store state.
INDEX_STATE Per-index configuration, table-column binding, lifecycle, and entry counts.
BACKEND_HEALTH Whether a per-index backend is loaded and writable, plus error code and external manifest state.
SYNC_PIPELINE Per-index pending changes, latest apply latency, and rebuild/recover progress.

6.2 Status Field Meanings

INDEX_STATE fields include dimension, metric, mode, provider, backend variant, table binding names, HNSW/Faiss/DiskANN tuning parameters, lifecycle state/version, mutation support, serving entry count, and committed entry count. A value of 0 for backend-specific tuning fields means the backend does not use that parameter or automatic/default behavior is active.

BACKEND_HEALTH fields include backend type, variant, mode, loaded/writable flags, the latest lifecycle error code and timestamp, recovery fallback counters, and external sidecar manifest presence/generation. After successful DiskANN native bulk/rebuild, external_manifest_present is 0 because the serving graph comes from the native store and committed-entry fallback.

SYNC_PIPELINE fields:

Field suffix Meaning
pending_apply_count Non-negative difference between entry_count and committed_entry_count; during bulk-load it usually equals the number of committed entries not yet served by the backend.
apply_latency_ms Time spent by the latest apply operation.
rebuild_progress Rebuild state indicator: 100 means ready, 50 means rebuilding, and other states report 0.
recover_progress Recovery state indicator: 100 means ready, 50 means recovering, and other states report 0.

Lifecycle state values:

Value Meaning
ready The index is readable and writable, and the latest create, rebuild, recover, or commit has completed.
creating Table-level CREATE VECTOR INDEX metadata has been persisted but backfill has not started; restart recovery removes this incomplete DDL state.
backfilling Table-level CREATE VECTOR INDEX is scanning the base table and building the initial committed/serving snapshot; queries fail, and restart recovery removes this incomplete DDL state.
bulk_loading The index is in bulk-load mode. Commits update only truth rows; queries fail until VEC_INDEX_BULK_BUILD() or VEC_INDEX_REBUILD() succeeds.
rebuilding The serving index is being rebuilt. The current synchronous rebuild API builds a shadow backend outside the lock, so this is usually visible only through explicit diagnostic state.
recovering The index is recovering from persistent state or committed entries. The current synchronous recover API builds a shadow backend outside the lock, so this is usually visible only through explicit diagnostic state.
failed The latest lifecycle operation failed; inspect last_error_code and last_error_ts.

Error codes:

Error code Meaning
0No error.
1001Uncommitted changes exist, so the current operation cannot safely execute.
1002Backend creation failed.
1003Backend recovery failed.

7. Usage Recommendations

  • Use VEC_FROMTEXT(...) consistently for text vector input to avoid client-side binary encoding differences.
  • For production table-column paths, prefer table-level DDL with normal DML because synchronization behavior is more direct.
  • Before tuning HNSW / Faiss / DiskANN, confirm the current index mode/provider.
  • When consuming machine-readable results, treat VEC_INDEX_INFO() / VEC_INDEX_SEARCH*() as JSON text.
  • After changing index parameters in batches, explicitly run VEC_INDEX_REBUILD(...) when build-time settings must take effect immediately.

7.1 Benchmark and Load Testing Experience

  • Before integrating an external benchmark, run a small dataset first to confirm table creation, index creation, writes, queries, and parameter mapping, then switch to a large dataset.
  • For high-dimensional large-batch imports, prefer the standalone named-index fast path:
    • Create the index with VEC_INDEX_CREATE.
    • Stage vectors in batches with VEC_INDEX_STAGE_UPSERT.
    • Commit each batch with VEC_INDEX_TXN_COMMIT.
    • Build the serving index once with VEC_INDEX_BULK_BUILD or VEC_INDEX_REBUILD.
    • Run queries with VEC_INDEX_SEARCH.
  • Large imports should pass binary float32 vector payloads directly from the client. VEC_FROMTEXT('[...]') is better for SQL examples, small smoke tests, and manual diagnostics.
  • Long-running load tests should use an isolated mysqld instance and reserve enough innodb_redo_log_capacity, innodb_buffer_pool_size, and backend build threads, so redo recycling, buffer pool churn, or low parallelism is not mistaken for a vector-index bottleneck.
  • If a benchmark runner separates load, optimize, and search into different processes, later processes should first call VEC_INDEX_INFO(index_name) to attach to existing index state instead of blindly repeating VEC_INDEX_CREATE(...).
  • If VEC_INDEX_INFO() already reports the target search_ef, repeated VEC_INDEX_SET_SEARCH_EF(...) is usually unnecessary; reissuing it only updates metadata/manifest.
  • When a load test becomes slow or interrupted, first distinguish whether the client import path or the server index build path is slow:
    • Use SHOW PROCESSLIST to see the SQL currently running in each session.
    • Use SHOW GLOBAL STATUS LIKE 'Vector_%' to inspect write, commit, persist, and search counters.
    • Use SHOW ENGINE INNODB STATUS to inspect truth-store, manifest, and change-log persistence summaries.
  • The current public ANN API has no native filter parameter. To validate filter semantics, write it as an exact query such as WHERE ... ORDER BY VEC_DISTANCE(...) LIMIT k. Do not describe over-fetch or post-filter results as native ANN filtering.
  • When validating non-default DiskANN parameters, record them in the test configuration:
    • DISKANN_MAX_DEGREE
    • DISKANN_BUILD_COMPLEXITY
    • DISKANN_SEARCH_COMPLEXITY
